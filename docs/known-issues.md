## Found by the E2E suite

**`A` selects about half the panes it should when sessions hold several panes each.**
`inboxCapacity` (`internal/ui/render.go`) assumes the worst case unconditionally —
`height / 2`, i.e. one session header for every pane — while the real header count is
knowable, because every pane in the list carries its session.

Measured end to end on a 24-row screen with 10 panes across 5 sessions:

| width | `VisiblePanes` claimed | renderer actually drew |
|---|---|---|
| 80 | 22 | 24 |
| 120 | 11 | 20 |
| 200 | 11 | 20 |

The direction is SAFE — it selects fewer than are visible, never more, which is the
property `A` exists to guarantee and the reason the estimate was made conservative in
the first place. But 11 of 20 is not the "one row fewer" the comment describes: it is
`A` silently doing half its job, and "select every visible pane" is what the key is
documented to do.

No unit test could see this: the one guarding the estimate asserts `count >= bodyH/2`,
which 11 satisfies. It took driving the real renderer against the real viewport at three
widths to surface it — which is the argument for the E2E suite in one line.

Ruling: real, safe-direction, worth fixing by counting the actual session groups in the
pane list rather than assuming one header per pane. Until then the E2E case asserts the
contract that HOLDS — never more than drawn — and records the shortfall in its output, so
the gap is visible without a permanently red suite.

**Scope, since the filesystem view became the default (docs/design.md §23):** this is a
defect of the FLAT list only, and it cannot exist on the default screen. There every drawn
line is exactly one thing, so `treeRowsOnScreen` asks the two functions the paint itself
asks (`treeListHeight` and `windowStart`) and the assertion is `count == drawn` rather than
a bound. The flat list keeps the estimate, and keeps this entry, for as long as it is
reachable with `t` and `--view=flat`.

## From the lifecycle branch closeout (Task 16)

**`tmux.KillSession` is built, tested and unwired.** §19 "Lifecycle" lists "Kill a session"
among the verbs, but the `K` key calls `tmux.KillWindow` only (`internal/ui/lifecycle.go:184`).
The function exists in `internal/tmux/lifecycle.go:96`, has test coverage, and no production
caller.

Ruling: §19 overpromises. Either the docs must be corrected to say the hub kills windows
(not sessions), or killing a session is future work and §19 should scope it as such. Until
decided, the wiring floor exempts `tmux.KillSession` as "built but unwired" so the question
remains visible in the test.

**`tmux.PaneAlive` is deliberately kept with no caller.** The function
(`internal/tmux/lifecycle.go:126`) checks whether a pane still exists and is tested, but has
no production call site. Task 14's comment in `internal/ui/lifecycle.go:22` explains why:
restart-in-place (`R` key) is safe by construction because `respawn-pane -k` kills then spawns
in one call, so no `PaneAlive` check is needed. The non-exclusivity of `claude --resume` is a
measured hazard (a second resume of a live session returns rc=0, no lock, two processes
appending to one transcript), but it is only reachable through resuming into a DIFFERENT pane.

Ruling: kept deliberately for a future resume-elsewhere path. Any such path must call
`PaneAlive` before resuming to refuse while the owning pane still holds the session. The
wiring floor exempts it so the question is visible. Do not delete the function; wire it when
the feature is built.

**E2E test `TestE2ERemoteLaunchPaneIsNotWalkedAgainstLocalProcs` is intermittently flaky.**
Observed twice: failed once with `control socket did not appear: stat … /ssh-ctl: no such file
or directory`, then passed 41/41 on the immediately following run (both runs by team-lead,
2026-08-12). The test creates a mock ssh master and expects the control socket file to appear;
the timing is occasionally off.

Ruling: real but intermittent ssh control socket setup race. All other remote tests pass
consistently, including `TestE2ERemotePollSeesRemotePanes`, `TestE2ERemoteSendDeliversToRemotePane`,
and `TestE2ERemoteTickLatency`. If this test fails, re-run the suite once before treating it
as a real failure. If it fails twice consecutively, treat as real.
